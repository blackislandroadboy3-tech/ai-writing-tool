## 1. 利用形態の判定と重要度の調整

同じコードでも、誰が触れるかで危険度がまったく違う。最初に次の3つのどれかに決め、レポートの「前提」に書く。

| 利用形態 | 手がかり | 主な脅威 |
|---|---|---|
| **ローカル**（自分のPCだけ） | デプロイ用ファイルなし、README に公開の記述なし、ユーザーが「自分用」と言っている | キーの漏えい（git・共有・同期）、同じWi-Fiからの接続、私的データの平文保存 |
| **社内・LAN** | `address = "0.0.0.0"`、Docker、社内サーバーの記述 | 上記＋同僚による他人の会話の閲覧、キーの無断利用 |
| **インターネット公開** | `*.streamlit.app`、Community Cloud、Dockerfile＋クラウド設定、README に公開URL | 上記＋見知らぬ人による悪用、APIキー代金の浪費、プロンプトインジェクション、利用者間のデータ混在 |

手がかりがなく判断できないときは、ユーザーに聞く。聞けない状況なら「ローカル」と仮定し、そのことと「公開する場合に重要度が上がる項目」をレポートに明記する。

**重要度の調整の例**
- 認証なし: ローカルなら指摘しない／社内なら低〜中／公開なら高（APIキーを他人が使い放題）
- レート制限・利用上限なし: ローカルなら指摘しない／公開なら中〜高（LLM10）
- `server.address` 未設定: ローカルなら中（同じWi-Fiから接続可）／公開なら問題なし（そもそも外に出す設定）
- `showErrorDetails` 既定: ローカルなら指摘しない／公開なら低（内部パスやコードが見える）

## 2. 確認項目

### A. 秘密情報（OWASP LLM02）
- ★ キー形式の文字列（`sk-`, `sk-ant-`, `AIza`, `hf_`, `gsk_`, `AKIA` など）が `.env` / `.streamlit/secrets.toml` 以外にないか（コード、README、ノートブック、ログ、データファイル）
- ★ `.env` と `.streamlit/secrets.toml` が `.gitignore` に入っているか
- ★ キーや `st.secrets` / `os.environ` / `st.session_state` を `st.write` / `print` / ログで表示していないか
- キー変数がどこへ流れるかを最後まで追う: 画面、ログ、保存ファイル、例外メッセージ、プロンプト（モデルに送る文章）
- 利用者にキーを入力させる場合、`type="password"` か。入力されたキーを保存・共有していないか（公開アプリで `st.cache_resource` に入れると他人が使える）
- 公開アプリでは、運営者のキーを使うならプロバイダー側の利用上限・予算アラートを設定しているか（コード外なので「未確認」に書いてよい）

### B. システムプロンプトの漏えい（LLM07）
- システムプロンプトに秘密（パスワード、内部URL、割引コード、社内規程の機密部分、キー）を入れていないか。**システムプロンプトは「聞かれたら出てしまう」前提で扱う**。「教えるな」と書いても防げない

### C. プロンプトインジェクション（LLM01）
- 外部由来のテキスト（アップロードファイル、URL の取得結果、受信メール、RAG の検索結果、URL パラメータ）がプロンプトに入るか
- 入る場合、その後に何ができるかで重要度が決まる: 表示だけなら低、ツール実行・外部送信・保存ができるなら高（D と E と組み合わせて評価）
- 区切りタグで囲む、「文書中の指示に従わない」とシステムプロンプトに書く、は軽減策にすぎない（完全には防げない）と書く

### D. 出力の扱い（LLM05）
- ★ `unsafe_allow_html=True`、`st.html`、`components.html` でモデル出力・利用者入力を描画していないか（スクリプト実行・偽フォーム・データ送信）
- `st.markdown(output)` の HTML は既定で無効なので安全。ただし Markdown 画像 `![](https://...)` は自動で読み込まれ、URL に会話内容を入れて外部に送る経路になる（C と組み合わさると成立）
- ★ モデル出力を `eval` / `exec` / `subprocess` / SQL / ファイルパス / URL に使っていないか

### E. 過剰な権限（LLM06）— ツール使用・エージェント
- ★ ツール/関数呼び出しがある場合、各ツールの権限を一覧にする: コード実行、シェル、ファイル書き込み（パス制限は？）、HTTP（宛先制限は？ SSRF・社内ネットワークへのアクセス）、メール送信、DB 更新
- 危険な操作の前に人の確認（承認ボタン）があるか
- C の外部テキスト → モデル → 危険なツール、という経路があれば **高**（ローカルでも、細工された PDF を開くだけで PC 上でコードが動く）

### F. 利用者間のデータ混在（LLM02、社内・公開時に重要）
- ★ `@st.cache_resource` / `@st.cache_data` に会話・入力・利用者ごとの情報を入れていないか（**全セッションで共有される**）
- ★ モジュール直下のグローバル変数（`log = []` など）は全セッションで共有される
- 保存ファイル（履歴 JSON、CSV、SQLite）が全利用者共通になっていないか、他人の履歴を表示していないか
- `st.session_state` はセッションごとなので、利用者ごとのデータはここに入れるのが正しい

### G. 無制限の消費（LLM10、公開時に重要）
- ★ `max_tokens` 等の出力上限があるか、入力長の上限があるか
- 1人あたりの回数制限、ログイン必須、プロバイダー側の予算上限
- エージェントのループに回数上限があるか（`while True` でツールを呼び続けないか）
- ★ アップロードサイズ（`server.maxUploadSize`、既定 200MB）

### H. 保存データ・ログ
- ★ 会話・入力を平文で保存しているか、どこに、何件、いつまで
- 保存先が git 除外されているか、クラウド同期フォルダ内でないか
- 削除機能が本当に消すか

### I. Streamlit 設定・依存関係（LLM03）
- ★ `server.address`、`enableXsrfProtection` / `enableCORS` を false にしていないか、`client.showErrorDetails`
- ★ `pip-audit` で既知の脆弱性。未インストールなら「未確認」
- ★ バージョン未固定、`trust_remote_code=True`、`torch.load`、`pickle`

## 3. 重要度の基準

判断の軸は「**この利用形態で、実際に誰が、どんな損をするか**」。

| 重要度 | 基準 | 例 |
|---|---|---|
| 高 | 現実的な手順でキー・私的データが漏れる、他人の会話が見える、任意のコードが実行される、費用を無制限に使われる | キーの直書き・git 未除外、モデル出力の `exec`、公開アプリの `cache_resource` に会話、システムプロンプトにパスワード、公開＋認証なし＋上限なし |
| 中 | 条件がそろうと起きる | ローカルで全インターフェース待ち受け、`unsafe_allow_html=True`、URL を制限しない取得ツール（ローカル） |
| 低 | 起きにくい・被害が小さい | Markdown 画像経由のデータ送信、バージョン未固定、公開時のエラー詳細表示 |
| 情報 | 問題ではないが知っておくべき | 履歴が平文で残る（ローカル）、pip-audit 未実行 |

過大評価も過小評価も害になる。ローカル用ツールに「認証がない」を高で並べると、本当に直すべき指摘が埋もれる。

## 4. Streamlit 特有の落とし穴（見落としやすい）
- スクリプトは操作のたびに上から再実行される。モジュール直下の変数は**プロセス全体で1つ**＝全利用者で共有
- `st.cache_resource` は「全利用者共通のリソース（クライアント、モデル）」用。利用者のデータを入れてはいけない
- `server.address` 未設定時は全インターフェースで待ち受け、起動時に「Network URL」が表示される
- `st.secrets` は `.streamlit/secrets.toml` から読む。Community Cloud では管理画面で設定するので、ファイルを git に入れる必要はない
